# Delta for schema-sync

## ADDED Requirements

New domain `schema-sync`: FKs emitted only when column charset/collation/type are compatible; sync/resync services centralized in core. Canonical at `openspec/specs/schema-sync/spec.md` after archive.

| ID | Requirement |
|----|-------------|
| SS-01 | FK MUST be emitted only when referenced column charset/collation/type match the local FK column |
| SS-02 | When compatibility cannot be determined, the FK MUST NOT be omitted |
| SS-03 | FK compatibility MUST be validated by ONE shared core validator in BOTH schema builders |
| SS-04 | A previously omitted FK MUST be re-attempted by a later sync via constraint comparison |
| SS-05 | Dependency-ordered schema sync/resync MUST be served by core-owned services |
| SS-06 | system_updater MUST NOT load against a core lacking the centralized classes |

### Requirement: SS-01 — Defensive FK creation

The system MUST verify referenced vs local FK column charset, collation and type before emitting a FOREIGN KEY in CREATE TABLE DDL. On incompatibility (e.g. utf8mb3 vs utf8mb4), it MUST omit the FK, log a warning, and still create the table, never failing with MySQL errno 150. When compatible, the FK MUST be emitted.

#### Scenario: FK to utf8mb3 parent omitted on mismatch

- **GIVEN** a local FK column utf8mb4_general_ci referencing a utf8mb3_general_ci column
- **WHEN** the schema sync generates the CREATE DDL
- **THEN** the FK is omitted, a warning logged, and the table created without errno 150

#### Scenario: FK emitted when columns are compatible

- **GIVEN** a local FK column matching the referenced column's charset, collation and type
- **WHEN** the schema sync generates the CREATE DDL
- **THEN** the FK is emitted exactly as defined

### Requirement: SS-02 — Permissive default

The system MUST NOT omit an FK when compatibility cannot be determined: non-MySQL engines per `FS_DB_TYPE`, non-collatable types (e.g. int), or missing metadata.

#### Scenario: Non-MySQL engine keeps the FK

- **GIVEN** a non-MySQL `FS_DB_TYPE` (e.g. PostgreSQL)
- **WHEN** the sync validates FK compatibility
- **THEN** the FK is allowed

#### Scenario: Non-collatable column type keeps the FK

- **GIVEN** an FK on a non-collatable column type (e.g. int)
- **WHEN** the sync validates FK compatibility
- **THEN** the FK is allowed

#### Scenario: Missing metadata keeps the FK

- **GIVEN** referenced column charset/collation/type cannot be retrieved
- **WHEN** the sync validates FK compatibility
- **THEN** the FK is allowed

### Requirement: SS-03 — Shared validator used by BOTH builders

The system MUST validate FK compatibility with ONE shared core validator (`src/Database/FkCompatibilityValidator`) from BOTH the `SchemaComparator` path and the `fs_schema` path (`addForeignKeyConstraint`); the builders MUST NOT diverge in FK behavior.

#### Scenario: Both builders delegate to the same validator

- **GIVEN** an FK-bearing CREATE generated by either the SchemaComparator path or the fs_schema path
- **WHEN** compatibility is validated
- **THEN** both paths use the same validator and make identical omit/keep decisions

### Requirement: SS-04 — Self-healing via constraint comparison

The system MUST re-attempt adding an FK omitted due to incompatibility when a later sync finds the columns aligned, via the existing `compare_constraints` path, without manual intervention.

#### Scenario: Omitted FK is recovered after columns align

- **GIVEN** an FK omitted at CREATE time due to collation mismatch
- **WHEN** a later sync runs after the columns become aligned
- **THEN** the constraint-comparison path re-adds the FK without manual intervention

### Requirement: SS-05 — Centralized sync services in core

The system MUST serve dependency-ordered schema sync and resync through core-owned `src/Core/Plugin/PluginUpdateOrderer` and `src/Core/Plugin/PluginSchemaResyncer` (generalized from `system_updater`). Plugins MUST reuse these instead of owning duplicates; the core MUST own the canonical implementation.

#### Scenario: Plugin delegates to core orderer and resyncer

- **GIVEN** a plugin needing dependency-ordered schema sync or resync
- **WHEN** the plugin performs the operation
- **THEN** it uses the core-owned classes and ships no duplicates

### Requirement: SS-06 — system_updater delegation + delivery coupling

When `system_updater` uses the core classes, its `fsframework.ini` `min_version` MUST be bumped to the core release that ships them (currently "0.13" is stale), so the plugin never loads against a core lacking them. Plugin call sites MUST remain API-compatible.

#### Scenario: min_version gates loading against an older core

- **GIVEN** a core version older than the one shipping the centralized classes
- **WHEN** system_updater attempts to load
- **THEN** loading is blocked by the updated `min_version` and call sites remain API-compatible
